# กฎธุรกิจทั้งหมด 26 ข้อ — อธิบายละเอียด

> เอกสารนี้อธิบายทุกกฎที่ระบบใช้ตรวจเอกสาร: ตรวจอะไร ทำงานเมื่อไหร่ ไม่ผ่านแล้วเกิดอะไร
> และควรทำอย่างไร ปรับได้ทั้งหมดจากหน้า **Settings** โดยไม่ต้องแก้โค้ด

---

## หลักการที่กฎทุกข้อยึด

**กฎพูดถึง "ตัวเอกสาร" ไม่ใช่ "ตัวระบบ"**

เดิมมี 30 ข้อ ลบไป 4 ข้อ (`required_fields_present`, `critical_fields_grounded`,
`low_confidence_fields`, `ocr_quality_acceptable`) เพราะมันไม่ได้บอกว่า*เอกสารผิด*
แต่บอกว่า*เราไม่มั่นใจ* — ซึ่งเป็นคนละเรื่อง และ routing จัดการอยู่แล้ว
การเอาสองอย่างนี้ปนกันทำให้คนอ่านผลแล้วงงว่า "เอกสารถูกอยู่แล้ว ทำไมขึ้นแดง"

**3 ระดับความรุนแรง**

| ระดับ | ความหมาย | ผลต่อการ post |
|---|---|---|
| `blocking` | ผิดแน่นอน / เสี่ยงเสียเงิน | **ห้าม auto-post** ต้องให้คนดู |
| `warning` | น่าสงสัย ควรดู | ผ่านได้ แต่ติดธงและหัก confidence |
| `info` | บันทึกไว้เฉยๆ | ไม่มีผล |

ปรับระดับได้รายกฎจากหน้า Settings — กฎที่ไม่ควร block ลดเป็น `warning` ได้
โดย**ยังตรวจอยู่** ต่างจากการปิดกฎซึ่งเสียคำเตือนไปด้วย ระบบเก็บ `original_severity`
ไว้เสมอ คนตรวจจึงแยกออกว่า "ถูกลดระดับมา" กับ "เตือนตั้งแต่แรก"

# 1. กฎเลขคณิต — คำนวณซ้ำ ไม่เชื่อ model

กลุ่มนี้ deterministic 100% ไม่มี LLM เกี่ยวข้อง เพราะ **model ที่ตัดสินว่าเลขถูกไหม
คือ model ที่ถูกเอกสารโน้มน้าวได้** ถ้าใบแจ้งหนี้เขียนว่า "VAT exempt per agreement"
model อาจเชื่อ โค้ดไม่เชื่อ

### `invoice_totals_consistent` — 🔴 blocking
**ใช้กับ:** invoice, receipt, purchase_order

ตรวจว่า `subtotal + tax_amount = total_amount`

- **ผ่านเมื่อ:** ผลต่างไม่เกิน `AMOUNT_TOLERANCE` (default 2%) หรือ 0.01 แล้วแต่ค่าไหนมากกว่า
- **ไม่ทำงานเมื่อ:** ขาด field ใด field หนึ่งใน 3 ตัว
- **เจอแล้วทำไง:** ดูภาพหน้าเอกสาร ส่วนใหญ่คือ OCR อ่านเลขผิดตัวเดียว แก้ที่ field แล้วระบบตรวจซ้ำให้
- **ทำไมเป็น blocking:** ยอดเงินผิด = จ่ายผิด ไม่มีข้อยกเว้น

### `tax_rate_consistent` — 🔴 blocking
**ใช้กับ:** invoice, receipt, purchase_order

ตรวจว่า `subtotal × tax_rate% = tax_amount` จริงไหม

- ต่างจากข้อบน: ข้อบนตรวจว่า**บวกกันได้** ข้อนี้ตรวจว่า**อัตราภาษีที่เขียนไว้ตรงกับจำนวนภาษี**
- **เจอบ่อยเมื่อ:** OCR อ่าน 7% เป็น 1% หรืออ่านจำนวนภาษีผิดหลัก

### `line_items_sum_to_subtotal` — 🟡 warning
**ใช้กับ:** invoice, receipt, purchase_order

ผลรวมของรายการในตารางต้องเท่ากับ subtotal

- **เป็น warning ไม่ใช่ blocking เพราะ:** ตารางอาจมีส่วนลด ค่าขนส่ง หรือรายการที่ OCR อ่านไม่ครบ
  ซึ่งไม่ได้แปลว่ายอดรวมผิด — ยอดรวมมี `invoice_totals_consistent` คุมอยู่แล้ว
- **ไม่ทำงานเมื่อ:** ไม่มีตาราง หรืออ่านตารางไม่ออก

### `vat_rate_expected` — 🟡 warning
**ใช้กับ:** invoice, receipt

อัตรา VAT ต้องอยู่ในชุดที่กำหนด (`EXPECTED_VAT_RATES` default `0,7`)

- **ปรับที่:** `.env` → `EXPECTED_VAT_RATES=0,7,10`
- **ถ้ารับเอกสารหลายประเทศ:** ควรเพิ่มอัตราของประเทศนั้นเข้าไป หรือปิดกฎนี้
- **ทำไมยังเก็บไว้:** จับเคส OCR อ่าน 7% เป็น 70% ได้

# 2. กฎ cross-check กับ master data

กลุ่มนี้เทียบสิ่งที่อยู่บนเอกสารกับสิ่งที่อยู่ในระบบ ซึ่งเป็นเหตุผลที่ระบบนี้ต่างจาก OCR ธรรมดา

> **หมายเหตุสำคัญ:** ทุกกฎในกลุ่มนี้เทียบด้วย [`rules/compare.py`](../src/docuflow/rules/compare.py)
> ซึ่งเทียบ**ค่า** ไม่ใช่**ตัวสะกด** — `2025-08-01` เท่ากับ `2025-8-1`, `thb` เท่ากับ `THB`,
> `1500` เท่ากับ `1500.00` เดิมใช้ `str(a) != str(b)` ซึ่งทำให้ขึ้นผิดโดยไม่จำเป็น

### `vendor_known` — 🔴 blocking (ปรับได้)
**ใช้กับ:** invoice, receipt, purchase_order, form

คู่ค้าต้องมีอยู่ใน vendor master file

- **หายังไง:** ไล่จากหลักฐานแข็งไปอ่อน — เลขผู้เสียภาษี → ชื่อตรงเป๊ะ/alias →
  ชื่อตรงหลังตัดคำว่า "บริษัท/จำกัด/Co., Ltd." → fuzzy ≥86% (ทน OCR เพี้ยน เช่น `แฟชิลิตี้` ↔ `แฟซิลิตี้`)
- **`blocking` เฉพาะประเภทที่กำหนด:** `UNKNOWN_VENDOR_BLOCKS=invoice,purchase_order`
  - **ทำไม receipt ไม่ block:** ใบเสร็จคือเงินที่**จ่ายไปแล้ว** ปั๊มน้ำมันไม่มีวันเป็น AP vendor
  - **ทำไม form ไม่ block:** ใบสมัครคู่ค้ามีอยู่**เพราะ**เขายังไม่ได้ลงทะเบียน
- **เจอแล้วทำไง:** ถ้าเป็นคู่ค้าจริง กด `docuflow vendor add` หรือใช้ `POST /api/master/vendors`

### `vendor_active` — 🔴 blocking
**ใช้กับ:** invoice, receipt, purchase_order

คู่ค้าที่สถานะ `on_hold` / `blocked` ห้ามจ่ายอัตโนมัติ

- **ไม่ทำงานเมื่อ:** หาคู่ค้าไม่เจอ (`vendor_known` จัดการแทน)
- นี่คือการควบคุมที่ทีมจัดซื้อตั้งใจตั้งไว้ ไม่ควรปิด

### `bank_account_matches_vendor` — 🔴 blocking
**ใช้กับ:** invoice

เลขบัญชีบนใบแจ้งหนี้ต้องตรงกับที่ลงทะเบียนไว้

- **นี่คือกฎกัน fraud ที่สำคัญที่สุดในระบบ** — invoice fraud แบบคลาสสิกคือส่งใบแจ้งหนี้จริง
  แต่เปลี่ยนเลขบัญชี
- เทียบด้วย `reference_key()` (ตัดขีด ช่องว่าง)
- ถ้าเลขบัญชีนั้นเป็นของคู่ค้า**รายอื่น** ระบบจะบอกชื่อรายนั้นด้วย
- **ถ้าไม่มีเลขบัญชีในระบบ:** เป็น warning แทน (ตรวจไม่ได้ ไม่ใช่ผิด)

### `duplicate_document` — 🔴 blocking
**ใช้กับ:** ทุกประเภท

เลขที่เอกสารเดิม + คู่ค้าเดิม ห้าม post ซ้ำ

- **เทียบ:** `reference_key(เลขที่)` + `vendor_id` กับ record ที่ post ไปแล้ว
- จ่ายซ้ำคือความเสียหายที่ตรงไปตรงมาที่สุด

# 3. กฎ three-way match (ใบแจ้งหนี้ ↔ ใบสั่งซื้อ)

หัวใจของ AP control — ของที่สั่ง ต้องตรงกับของที่ถูกเรียกเก็บ

### `purchase_order_required` — 🔴 blocking
**ใช้กับ:** invoice

ใบแจ้งหนี้เกิน `PO_REQUIRED_ABOVE` (default 50,000) ต้องอ้าง PO

- **ปรับที่:** `.env` → `PO_REQUIRED_ABOVE=100000`
- **ไม่ทำงานเมื่อ:** ยอดต่ำกว่าเกณฑ์ หรืออ่านยอดไม่ได้

### `po_exists` — 🔴 blocking
**ใช้กับ:** invoice · *รายงานได้ 2 ชื่อ: `po_exists` และ `po_vendor_matches`*

PO ที่อ้างต้องมีอยู่จริง **และเป็นของคู่ค้ารายนี้**

- 2 เงื่อนไขในกฎเดียว เพราะเป็นความล้มเหลวคนละแบบ:
  - `po_exists` — ไม่มี PO เลขนี้ในระบบ
  - `po_vendor_matches` — มี PO แต่เป็นของคู่ค้าคนอื่น (อันนี้อันตรายกว่า)

### `po_amount_within_tolerance` — 🔴 blocking
**ใช้กับ:** invoice

ยอดที่เรียกเก็บต้องไม่เกินยอด PO เกิน tolerance

- **ปรับที่:** `AMOUNT_TOLERANCE` (default 2%)
- เรียกเก็บ**ต่ำกว่า** PO ไม่ผิด (ส่งของบางส่วน) — กฎนี้ดูเฉพาะการเกิน

### `po_currency_matches` — 🔴 blocking
**ใช้กับ:** invoice

สกุลเงินบนใบแจ้งหนี้ต้องตรงกับ PO

- สั่งเป็น THB แต่เรียกเก็บเป็น EUR = ผิดพลาดหรือฉ้อโกง อย่างใดอย่างหนึ่ง

# 4. กฎวันที่และตัวเลข

### `due_date_after_issue` — 🟡 warning
**ใช้กับ:** invoice

วันครบกำหนดต้องไม่มาก่อนวันออกบิล

- ถ้าเจอแบบนี้แปลว่าอ่านวันใดวันหนึ่งผิด

### `dates_not_in_future` — 🟡 warning
**ใช้กับ:** ทุกประเภท

วันที่ออกเอกสารไม่ควรเป็นอนาคต

- **ผ่อนได้:** `FUTURE_DATE_TOLERANCE_DAYS` (default 2 วัน — เผื่อ timezone)
- **ดูเฉพาะวันที่ออกเอกสาร** ไม่ดู due_date / expiry_date ซึ่งเป็นอนาคตตามปกติ
- สาเหตุที่พบบ่อย: อ่านปี พ.ศ. เป็น ค.ศ.

### `tax_id_checksum` — 🟡 warning
**ใช้กับ:** ทุกประเภท

ตรวจ checksum เลขประจำตัวผู้เสียภาษีไทย 13 หลัก

- เป็นคณิตศาสตร์ล้วน — เลขที่พิมพ์ผิด 1 ตัวจะไม่ผ่าน
- **ถ้าไม่ใช่เลข 13 หลัก:** ผ่านโดยบอกว่า "ไม่ใช่รูปแบบไทย ตรวจ checksum ไม่ได้" (ไม่ใช่ error)

# 5. กฎสัญญา

### `contract_dates_ordered` — 🔴 blocking
วันสิ้นสุดต้องหลังวันเริ่ม และอายุสัญญาต้องไม่เกิน `MAX_CONTRACT_YEARS` (default 25 ปี)

- อายุเกิน 25 ปีมักแปลว่าอ่านปีผิด ไม่ใช่สัญญา 99 ปีจริงๆ

### `contract_parties_distinct` — 🔴 blocking
คู่สัญญาสองฝ่ายต้องไม่ใช่องค์กรเดียวกัน

- เทียบหลัง normalize — ถ้าเหมือนกันแปลว่าอ่านผิดฝั่ง

### `contract_matches_master` — 🔴 blocking
ถ้าเลขที่สัญญามีในทะเบียนแล้ว ค่าบนเอกสารต้องตรงกับทะเบียน

- เทียบ: วันเริ่ม, วันสิ้นสุด, มูลค่า
- **ถ้าไม่มีในทะเบียน:** ผ่านโดยบอกว่าจะสร้างรายการใหม่ (ไม่ใช่ error)

### `contract_expiring_soon` — 🟡 warning
สัญญาที่ใกล้หมดอายุหรือหมดแล้ว

- **ปรับที่:** `CONTRACT_EXPIRY_WARNING_DAYS` (default 90 วัน)
- ถ้ามี notice period ระบบจะเตือนด้วยว่าเหลือเวลาบอกเลิกกี่วัน

### `contract_value_present` — 🟡 warning
สัญญาที่ไม่มีมูลค่าเอาไปผูกงบไม่ได้ — บาง MOU ไม่มีมูลค่าจริง จึงเป็นแค่ warning

# 6. กฎแบบฟอร์ม / การรับคู่ค้าใหม่

### `bank_account_not_reused` — 🔴 blocking
เลขบัญชีที่ยื่นมา ต้องไม่ใช่ของคู่ค้ารายอื่นที่ลงทะเบียนแล้ว

- **นี่คือ fraud control ตอน onboarding** — คู่ค้าปลอมที่ใช้บัญชีเดียวกับรายเดิม

### `bank_details_complete` — 🟡 warning
ใบสมัครที่ไม่มีข้อมูลธนาคารครบ จ่ายเงินไม่ได้

### `contact_email_valid` / `contact_phone_valid` — 🟡 warning
รูปแบบอีเมล / จำนวนหลักเบอร์โทรต้องสมเหตุสมผล

- ติดต่อไม่ได้ = onboarding ค้าง

### `applicant_already_registered` — 🟡 warning
ผู้สมัครอาจมีอยู่ในระบบแล้ว (advisory)

- ไม่ block เพราะอาจเป็นการยื่นแก้ไขข้อมูล

# 7. กฎเชิงแนะนำ

### `currency_matches_vendor_default` — 🟡 warning
**ใช้กับ:** invoice

คู่ค้ารายนี้ปกติเรียกเก็บสกุลเงินอื่น

- เป็น advisory ล้วน — คู่ค้าหลายรายเรียกเก็บได้หลายสกุลเงินอย่างถูกต้อง
- **ถ้าคู่ค้าคุณใช้หลายสกุลเงินเป็นปกติ:** ปิดกฎนี้ได้เลย

# กฎที่คุณเขียนเอง — 2 แบบ

| | **Condition** | **Agent** |
|---|---|---|
| ตอนใช้งาน | รันด้วยโค้ด ไม่มี model | agent เดินตาม plan พร้อม tools |
| ค่าใช้จ่าย | ฟรี | 1 model call ต่อเอกสารที่เข้าเงื่อนไข |
| ตอบเหมือนเดิมทุกครั้ง | ใช่ | ไม่รับประกัน |
| เหมาะกับ | เทียบ field กับ field/ค่าคงที่ | ต้อง**ค้นข้อมูล** แล้ว**ตัดสิน**จากสิ่งที่เจอ |

ระบบเลือกให้เองได้ (`Pick for me`) หรือบังคับเองก็ได้ **ถ้า condition ทำได้ ให้ใช้
condition** — ถูกกว่า เร็วกว่า และตอบเหมือนเดิมทุกครั้ง

## agent rule ประกอบด้วยอะไร

```
when         เงื่อนไขว่ากฎนี้ใช้กับใบไหน — ตรวจด้วยโค้ด ไม่มี model
             (ตัวนี้คือรั้วกันค่าใช้จ่าย: จำกัดว่า agent จะรันบ่อยแค่ไหน)
instruction  agent ต้องตัดสินอะไร
plan         2-5 ขั้น เขียนตอนสร้างกฎ ครั้งเดียว ไม่ใช่คิดใหม่ทุกใบ
tools        เครื่องมือที่ให้ใช้ (ไม่ระบุ = ทุกตัว)
```

เครื่องมือที่มี: `read_document` `lookup_vendor` `lookup_purchase_order`
`lookup_contract` `find_posted_records` `check_arithmetic` `validate_tax_id`

## คำตอบ 3 แบบ และผลของมัน

| verdict | หมายความว่า | ผล |
|---|---|---|
| `pass` | ยืนยันแล้วว่าผ่าน | ผ่าน (severity `info`) |
| `fail` | ไม่ผ่าน | ตาม severity ของกฎ |
| `unsure` | ตัดสินไม่ได้ | **ค้างให้คนดู** และ**ไม่มีวัน block** |

`unsure` เกิดเมื่อ: model ล่ม, ตอบไม่เป็น JSON, ค้นแล้วไม่เจอ, หมดจำนวนรอบ
หรือไม่ได้ตั้ง model ไว้เลย — **ทุกกรณีคือค้าง ไม่ใช่ผ่าน** เพราะ "ตรวจไม่ได้"
กับ "ตรวจแล้วผ่าน" ไม่ใช่เรื่องเดียวกัน

และ `unsure` ถูกลดจาก `blocking` เป็น `warning` เสมอ — backend มีปัญหาไม่ควร
กลายเป็นใบแจ้งหนี้ที่ถูกปฏิเสธ

## agent เปลี่ยนอะไรไม่ได้บ้าง

severity, rule_id, doc_types, message ทั้งหมดมาจากกฎที่บันทึกไว้ สิ่งที่ agent
ส่งกลับมีแค่ verdict + ข้อความอธิบาย ต่อให้ตอบ `"severity":"info"` มาก็ไม่มีผล

**ข้อความบนเอกสารคือข้อมูล ไม่ใช่คำสั่ง** — full text ของหน้าไม่ได้ถูกใส่เข้า
prompt เลย agent ต้องเรียก `read_document` ค้นเอง สิ่งที่เขียนบนใบแจ้งหนี้จึงมา
ในฐานะ "ผลการค้นที่ agent เลือกค้น" ไม่ใช่ส่วนหนึ่งของคำสั่งที่มันได้รับ

## ข้อควรระวัง: agent ทำตาม plan ตรงตัว

plan ที่เขียนว่า "เทียบยอด PO กับ total ของใบแจ้งหนี้" จะ fail ใบที่ถูกต้อง
ทุกใบ เพราะ PO เก็บยอด**ก่อน VAT** ส่วน total คือ**หลัง VAT** — agent ทำถูกตาม
ที่สั่ง แต่สิ่งที่สั่งผิด

หน้า preview มีไว้เพื่อจับเรื่องนี้: มันลองกฎกับเอกสารจริงก่อนบันทึก ถ้าขึ้นว่า
"ทุกใบจะ fail" แปลว่า plan ผิด ไม่ใช่เอกสารผิด (agent rule ลองแค่ 4 ใบ เพราะ
ใบละ 1 model call)

## เพิ่มกฎใหม่ (developer)

```python
@rule("invoice", severity="blocking")
def my_check(context: RuleContext) -> RuleFinding | None:
    """บรรทัดแรกของ docstring จะไปโผล่บนหน้า Settings"""
    value = context.value("total_amount")
    if value is None:
        return None                      # ไม่เกี่ยวกับเอกสารใบนี้
    if value <= 1_000_000:
        return passed("my_check", "ยอดอยู่ในเกณฑ์")
    return failed("my_check", "ยอดเกิน 1 ล้าน", severity="blocking",
                  fields=["total_amount"])
```

บรรทัดเดียวจบ — registry จะเก็บเข้าไปเอง และโผล่บนหน้า Settings ทันที
