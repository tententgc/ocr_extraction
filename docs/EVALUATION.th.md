## 2. วิธีการประเมิน

**ผลที่คาดไว้อยู่ในชื่อไฟล์** `_True` = ไม่มีอะไรผิด การหยุดมันคือ false alarm ·
`_False` = มีอะไรผิด การปล่อยผ่านคือ silent error

**สองอย่างนี้ไม่สมมาตร และห้ามบวกกัน** — พลาดข้อบกพร่อง = จ่ายเงินผิด ·
false alarm = เสียเวลาคนหนึ่งนาที

การอ่านสองรอบใช้ **backend คนละตัวโดยเจตนา** เพราะโมเดลเดียวกันอ่านหน้าเดิมสองครั้ง
จะผิดแบบเดิม การที่มันตรงกันจึงมีความหมายน้อยกว่าที่ตาเห็นมาก

เอกสารรันตามลำดับเลข เพราะเอกสาร 15 เป็นสำเนาซ้ำของเอกสาร 1 และตรวจไม่ได้จนกว่า 1 จะโพสต์ก่อน

### 2.2 วัดอะไรบ้าง และทำไมต้องมีทุกตัว

| การวัด | ตอบคำถามอะไร | ทำไมตัวอื่นตอบแทนไม่ได้ |
|---|---|---|
| **Precision / Recall** | ที่ตอบไป ถูกกี่ตัว · ที่มีอยู่ หาเจอกี่ตัว | accuracy อย่างเดียวมองไม่เห็นคลาสหายากที่ไม่เคยถูกจำแนกได้ และมองไม่เห็นค่าที่ระบบแต่งขึ้นเอง |
| **ความแม่นของ OCR** | อ่านหน้ากระดาษออกไหม | ฟิลด์ที่ผิดเพราะตัวอักษรไม่เคยมาถึง ไม่ใช่ปัญหาของ extraction และแก้ extraction ไม่ช่วย |
| **Data quality** | ข้อมูลส่งต่อระบบอื่นได้ไหม | ตัวเดียวที่ยังทำงานได้ใน production ซึ่งไม่มีเฉลย |
| **Gatekeeping** | เอกสารไปถูกทางไหม · กฎแต่ละตัวยิงเพราะเหตุที่มันมีอยู่ไหม | การนับคำตัดสินแยกไม่ออกระหว่างกฎที่ทำงาน กับกฎที่เงียบแต่บังเอิญมีกฎอื่นจับแทน |
| **Silent error rate** | ค่าสำคัญที่ผิดหลุดผ่านโดยไม่มีคนขวางไหม | ทุกตัวข้างบนดูดีได้ ทั้งที่ตัวนี้ไม่เป็นศูนย์ |
| **Latency & Cost** | ใช้ต้นทุนเท่าไร | การ optimise มีค่าก็ต่อเมื่อตัวเลขข้างบนไม่ขยับ |

### 2.3 สามอย่างที่ harness ปฏิเสธที่จะทำเงียบ ๆ

ทั้งสามอย่างดันตัวเลขไปในทาง**ที่ดูดีขึ้น** และทั้งสามอย่างเจอตอน**สร้าง** harness ไม่ใช่ตอนคิด

**1. ไม่ยอมตัดสินกฎที่ไม่เคยถูกถาม**

`Settings` เติมค่าที่ไม่ได้ระบุจาก `.env` ในเครื่อง — เครื่องนี้ปิดกฎไว้ 7 ตัว และ 2 ตัว
(`bank_account_matches_vendor`, `po_amount_within_tolerance`) เป็นกฎของเอกสารที่มีไว้เพื่อถูกหยุด
ปล่อยไว้ = รายงาน **missed defect 2 ตัว** ซึ่งแปลว่า "จ่ายเงินผิด" ด้วยเหตุผลที่อยู่ในไฟล์ที่ไม่ถูก track
harness เปิดกลับมาให้ แล้ว**บอกในรายงานว่าเปิดอะไรบ้าง**

**2. ไม่ยอมให้คะแนนกับข้อความที่ "คัดลอก" ไม่ใช่ "อ่าน"**

ทางลัด text layer คืนข้อความจาก PDF โดยตรง และ `reference_text` ก็มาจากที่เดียวกัน
เป็นสตริงเดียวกัน → **CER = 0 โดยนิยาม** 15 จาก 30 เอกสารใช้ทางนี้

| | ความแม่นตัวอักษร | Value recall |
|---|---|---|
| หน้าที่ engine อ่านจริง (15) | **86.8%** | **86.2%** |
| รวม text layer เข้าไป (30) | 93.7% | 91.6% |

ตัวแรกคือตัวที่ใช้อ้างเป็น OCR accuracy · ตัวหลังพิมพ์ไว้พร้อมป้ายกำกับ ไม่ได้ซ่อน

**3. ไม่ยอมตัดสินกับค่าที่หน้ากระดาษไม่เคยพิมพ์**

11 จาก 298 ค่า (3.7%) ที่ ground truth อ้าง แต่ไม่มีในข้อความที่ renderer วาดจริง:

| ฟิลด์ | จำนวน | เอกสาร | ทำไม |
|---|---|---|---|
| `purchase_order_ref` | 3 | 4, 16, 19 | layout `dense`/`two_column` ไม่มีบรรทัดใบสั่งซื้อ |
| `vendor_tax_id` | 2 | 6, 10 | `minimal` ไม่ใส่ label อะไรเลย — เป็นเจตนาของ layout |
| `payment_terms` | 2 | 6, 10 | layout เดียวกัน |
| `payment_method` | 2 | 11, 24 | ใบเสร็จไม่พิมพ์ |
| `due_date` | 2 | 7, 19 | คำนวณได้จากเงื่อนไขชำระ แต่ไม่เคยเขียนลงไป |

ค่าเหล่านี้จะรายงานว่า "หาไม่เจอ" กับ **ทุก engine ที่ใครก็ตามเอามาลอง** →
recall ข้างล่างต่ำกว่าความจริงประมาณเท่านี้

**แสดงรายการไว้ ไม่ตัดทิ้ง** — harness ที่แอบทิ้ง ground truth ที่ตรวจไม่ได้
คือ harness ที่ให้ตัวเลขดีขึ้นทุกครั้งที่ corpus แย่ลง

อีกสองข้อสังเกตเรื่อง corpus รายงานด้วยเหตุผลเดียวกัน:

- `18_invoice_unlabelled_amounts_True.jpg` มี text layer แค่ 196 ตัวอักษร
  พิสูจน์อะไรเกี่ยวกับ ground truth ไม่ได้ทั้งสองทาง
- `3_invoice_photo_on_a_desk_False.jpg` ต้องถูกหยุด แต่ไม่ประกาศกฎไหนเลย
  ข้อบกพร่องมีจริง — มันอ้าง `PO-2026-0545` ซึ่งเป็นใบสั่งซื้อ **ปิดแล้วใบเดียวในทะเบียน** —
  แต่เพราะไม่ได้เขียนไว้ กฎที่จับได้จึงถูกนับเป็น "ยิงเกิน" และ defect recall มองไม่เห็นมันเลย

**macro สำคัญแม้ตอนได้ 100%** — 23 จาก 30 เป็นใบแจ้งหนี้ ดังนั้นการตอบว่า "ใบแจ้งหนี้"
ทุกครั้งได้ **accuracy 77%** ทั้งที่**ไม่เคยรู้จักใบเสร็จเลยสักครั้ง**

และเรื่องนี้เกิดขึ้นจริงในโปรเจกต์นี้มาแล้ว เพราะเครื่องออกใบเสร็จไทยพิมพ์ว่า

ตอนนั้น macro recall ของ `receipt` จะเป็น 0 ส่วน accuracy จะบอกว่า 77%

## 4. อ่านหน้ากระดาษออกไหม

| | หน้าที่ engine อ่านจริง (15) | รวม text layer (30) |
|---|---|---|
| ความแม่นตัวอักษร | **86.8%** | 93.7% |
| อัตราตัวอักษรผิด (CER) | 13.20% | 6.3% |
| Value recall | **86.2%** (119/138) | 91.6% |

เอกสารที่อ่านได้แย่ที่สุด:

| เอกสาร | ตัวอักษร | ค่า | ที่หาย |
|---|---|---|---|
| `11_receipt_photographed_True.jpg` | 55.3% | 86% | `payment_method` |
| `24_receipt_clean_thermal_True.pdf` | 55.4% | 86% | `payment_method` |
| `16_invoice_line_items_do_not_sum_False.jpg` | 64.0% | 40% | เลขที่ใบแจ้งหนี้ + วันที่ทั้งสอง |
| `27_receipt_thai_fuel_station_True.jpg` | 69.4% | **100%** | — |

**ใบเสร็จสองใบที่ ~55% เป็นข้อควรระวังของ *ตัววัด* ไม่ใช่ของ engine** ใบเสร็จ 80 มม.
มีไม่กี่ร้อยตัวอักษร ตัวหารเลยเล็กมาก และการที่ OCR ตัดบรรทัดเรียบร้อยกว่าต้นฉบับ
ก็ครอบงำระยะแก้ไขทันที ทั้งสองใบยังได้ค่าที่สำคัญคืนมา 86% และ**ทุกจำนวนเงินถูกต้อง**

**ใบเสร็จน้ำมันภาษาไทยพิสูจน์ประเด็นนี้ชัดที่สุด: ตัวอักษร 69.4% แต่ค่าที่สำคัญ 100%**

ความต่างนี้คือเหตุผลที่ต้องรายงานสองตัวเลข — CER อธิบายข้อความทั้งหน้า ส่วน value recall
อธิบายตัวเลขที่จะกลายเป็นการจ่ายเงิน

สกุลเงินทุกตัวเป็นรหัส 3 ตัวอักษร · เปอร์เซ็นต์ทุกตัวอยู่ในช่วง

**ไม่มีค่าไหนถึง ledger ในรูปแบบที่ระบบอื่นต้องเดา** — ซึ่งเป็นที่ที่ความล้มเหลวเงียบ ๆ อาศัยอยู่:
อัตราภาษีที่เก็บเป็น `"7%"` จะไปถึงกฎ `tax_rate_consistent` แล้ว**ข้าม**แทนที่จะ**ตก**
กฎนั้นก็เลิกมีอยู่โดยไม่มีใครรู้

**ฟิลด์ที่ว่างถูกนับ ไม่ถูกตัดสิน** — ใบแจ้งหนี้ที่ไม่มีเลขใบสั่งซื้อก็เป็นใบแจ้งหนี้ที่ถูกต้อง
ส่วนที่ว่ามัน *จำเป็น* ไหม เป็นนโยบายธุรกิจและตั้งค่าได้

### 6.1 สองฉบับที่โพสต์ทั้งที่ผิด

**ทั้งคู่เป็นเอกสารไทย และเป็นความผิดพลาดแบบเดียวกัน:**

| เอกสาร | ฟิลด์ | ที่ถูก | ที่อ่านได้ | ความมั่นใจ |
|---|---|---|---|---|
| `25_invoice_thai_arabic_digits_True.png` | `vendor_name` | บริษัท สยาม**ซ**ัพพลาย จำกัด | บริษัท สยาม**ช**ัพพลาย จำกัด | 0.843 |
| `30_invoice_thai_no_tax_id_True.png` | `vendor_name` | บริษัท **ซ**ันไรส์ **อิ**เล็คทริคอล จำกัด | บริษัท **ช**ันไรส์ **อี**เล็คทริคอล จำกัด | 0.840 |

**ซ** (U+0E0B) กับ **ช** (U+0E0A) ต่างกันแค่หัวม้วนเดียว · **อิ** กับ **อี** ต่างกันแค่สระตัวเดียว
นี่คือคู่ที่ OCR ภาษาไทยสับสนกันเป็นประจำ

**สามอย่างที่ทำให้มันผ่านแทนที่จะถูกหยุด:**

1. **ไม่มีกฎไหนยิงเลย** — ทั้ง 33 ตัว
2. **ความมั่นใจตกลงพอดีที่เกณฑ์** — 0.843 และ 0.840 เทียบกับเกณฑ์ 0.840
   **ห่างกัน 0.003 กับ 0.000**
3. **`vendor_known` ผ่าน** — การจับคู่ผู้ขายใช้ fuzzy โดยเจตนา เพราะถ้าเทียบตรงตัว
   จะบล็อกทุกการอ่านผิดหนึ่งขีดของภาษาไทย มันจับคู่**ถูกราย** ดังนั้นเงินจะไปเข้าบัญชี
   ที่ลงทะเบียนไว้ ไม่ใช่ชื่อที่อ่านผิด

**ดังนั้น การจ่ายเงินถูก แต่บันทึกใน ledger ผิด** เป็นข้อบกพร่องด้านคุณภาพข้อมูล
ไม่ใช่การจ่ายเงินผิด และตัววัดไม่ได้แยกสองอย่างนี้ — ซึ่งถูกต้องแล้ว เพราะ
`vendor_name` ถูกประกาศว่าเป็นฟิลด์สำคัญ

**นี่คือข้อจำกัดที่รู้อยู่แล้ว แต่เพิ่งถูกวัดเป็นครั้งแรก**

> Grounding พิสูจน์ว่าค่ามาจากข้อความบนหน้ากระดาษ **แต่จับ OCR ที่อ่านผิดไม่ได้** —
> ข้อความนั้นมีอยู่จริงในผลลัพธ์ OCR และผลลัพธ์ OCR นั่นแหละคือสิ่งที่ผิด

สองช่องทางที่อ่านจากข้อความ OCR ชุดเดียวกันก็จับไม่ได้เหมือนกัน — **agent ทั้งสองตัวเห็น
`ชัพพลาย` เหมือนกัน** ส่วนแนวป้องกันที่เอกสารระบุไว้คือกฎเลขคณิตกับสัญญาณความชัดของหน้า
และทั้งสองอย่างมองไม่เห็นชื่อที่สะกดผิดบนหน้าที่ชัดเจน

**แต่มีสัญญาณที่ยังไม่ได้ใช้วางอยู่ตรงนั้นแล้ว**

`vendor_known` จับคู่ผู้ขายด้วย fuzzy match และ**บันทึกคะแนนไว้** ทะเบียนก็เก็บชื่อทางกฎหมาย
ที่ถูกต้องไว้ **ผู้ขายที่จับคู่ได้แบบ fuzzy แต่ชื่อที่สกัดมา *ไม่ตรง* กับชื่อในทะเบียน
คือหลักฐานตรง ๆ ว่าฟิลด์สำคัญถูกอ่านผิด** — และวันนี้คะแนนนั้นถูกบันทึกไว้เฉย ๆ
ไม่มีอะไรเอาไปใช้

นี่คือสิ่งแรกที่ควรแก้ และเป็นสิ่งที่ **การประเมินนี้ค้นพบ** ไม่ใช่แค่ยืนยัน

### 6.2 ภาษาไทยอ่านได้ดีกว่า แต่พังหนักกว่า

| | เอกสาร | ความแม่นของฟิลด์ | Silent errors |
|---|---|---|---|
| อังกฤษ | 22 | 88.2% | **0** |
| ไทย | 8 | **94.9%** | **2** |

**ความแม่นของฟิลด์ภาษาไทยสูงกว่าอังกฤษถึง 6 จุด และภาษาไทยแบกทั้งสอง silent error**

ไม่ได้ขัดกันเลย — ความผิดพลาดของภาษาไทยคือความสับสนอักษรตัวเดียวภายในชื่อ
ซึ่ง fuzzy vendor matching ดูดซับไป และการตรวจอื่น ๆ ทั้งหมดมองข้าม

**ความแม่นเฉลี่ย กับ ความปลอดภัยในกรณีเลวร้ายที่สุด เป็นคนละคำถามกัน**
และนี่คือหน้าตาของตอนที่สองอย่างนี้ไม่ตรงกัน

## 8. เวลาที่ประหยัด — เป็นแบบจำลอง ไม่ใช่การวัด

**สมมติฐานถูกพิมพ์คู่กับตัวเลขทุกครั้ง** เพราะตัวเลขที่จำลองขึ้นแล้วนำเสนอเหมือนตัวเลขที่วัดจริง
คือวิธีที่รายงานจบลงด้วยการอ้างการประหยัดที่ภายหลังไม่มีใครหาเจอ

| | นาที | ต่อ 1,000 เอกสาร |
|---|---|---|
| ทำด้วยมือ | 225 | 16.7 วัน |
| ผ่านระบบนี้ | 114 | 8.4 วัน |
| — ในนั้นเป็นงานตามแก้ | **90** | ตามเก็บ 2 เอกสารที่โพสต์ผิด |
| **ประหยัดได้** | **111 (49%)** | |
| เวลาเครื่อง | 19.8 | ไม่มีใครนั่งรอในการรันเป็นชุด |

สมมติฐานต่อเอกสาร: คีย์ข้อมูล 4.0 นาที · ตรวจทาน 3.5 นาที · ดูเอกสารที่ถูกหยุด 1.5 นาที ·
**ตามเก็บ silent error หนึ่งตัว 45 นาที**

**silent error สองตัวกินไป 90 นาทีในแบบจำลอง — คิดเป็น 80% ของการประหยัดทั้งหมด**

เลขคณิตชุดนี้**ตั้งใจเปิดให้สรุปได้ว่าระบบทำให้แย่ลง** และนี่คือระยะที่มันเข้าใกล้:
เอกสาร 2 ฉบับจาก 30 ดึงการประหยัดจาก 88% ลงมาเหลือ 49%

**นั่นคือเหตุผลทั้งหมดที่ silent error rate เป็นตัวเลขพาดหัว ไม่ใช่ความแม่นของฟิลด์**

## 9. สิ่งที่ควรทำต่อ เรียงตามลำดับ

1. **ใช้คะแนนการจับคู่ผู้ขาย** — ผู้ขายที่จับคู่ได้แบบ fuzzy แต่ชื่อที่สกัดมาต่างจากทะเบียน
   คือหลักฐานว่าฟิลด์สำคัญถูกอ่านผิด สัญญาณมีอยู่แล้วแต่ไม่มีอะไรอ่านมัน
   **นี่คือทางแก้ของ silent error ทั้งสองตัว**
2. **แก้ ground truth 11 ค่าที่หน้ากระดาษไม่พิมพ์** ใน `samples/real_world.py`
   เพื่อให้ recall เลิกต่ำกว่าความจริง 3.7% ตลอดไป
3. **ประกาศกฎของเอกสาร 3** เพื่อให้ใบสั่งซื้อที่ปิดแล้วซึ่งมันอ้าง ถูกนับเป็นข้อบกพร่องที่จับได้จริง
4. **เขียนเอกสาร corpus สำหรับกฎ 22 ตัวที่ยังไม่ถูกทดสอบ** — ยังไม่ถูกทดสอบ ไม่เท่ากับ ผ่าน
5. **ดูเรื่องระยะห่าง 0.003 จากเกณฑ์** — silent error ทั้งสองตัวนั่งอยู่บนเกณฑ์พอดี
   นั่นไม่ใช่เรื่องบังเอิญที่ควรมองข้าม

docuflow evaluate --corpus real_samples --out report.json
```

harness จะเปิดกฎที่ corpus ประกาศแต่ `.env` ในเครื่องปิดไว้ กลับมาให้ และบันทึกว่าเปิดอะไรบ้าง

docuflow evaluate --corpus real_samples --respect-disabled
```
