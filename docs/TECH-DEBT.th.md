## 1. `web/app.js` 2,053 บรรทัด ไม่มีเทสเลย 🔴

**หลุมใหญ่ที่สุด และเป็นที่ที่บั๊กจะสะสมเร็วที่สุด**

### หลักฐาน

Session เดียว (2026-08-05) เจอบั๊ก UI **5 ตัว** และ **เทส Python 753 ตัวจับไม่ได้สักตัว**:

| บั๊ก | อาการ |
|---|---|
| `.tabs { top: 63px }` ตายตัว | header สูงจริง 110px → scroll แล้ว tab bar มุดใต้ header 47px |
| `severity === 'blocking' ? 'bad' : 'warn'` | `info` ถูกทาสีส้มเตือน — ขัด invariant "สามระดับต้องต่างกัน" ของโปรเจกต์เอง |
| badge นับ `needs_review` แต่ตารางไม่กรอง | badge ขึ้น 5 กดเข้าไปเจอ 10 |
| `builtin_rules_disabled` notice | จมอยู่ในลิสต์ "ผ่านแล้ว" ที่พับไว้ — ที่ที่ไม่มีใครเปิดดู |
| ไม่มี `Cache-Control` | แก้ CSS แล้วไม่มีผล จนกว่าจะ hard reload |

สี่ในห้าตัวนี้**ผู้ใช้เห็นทันที** และตัวที่ 2 กับ 4 เป็นเรื่องความถูกต้อง ไม่ใช่ความสวย

### ต้องทำอะไร

เทส E2E ด้วย Playwright ประมาณ 10–15 เคส คลุมเฉพาะที่พังมาแล้วก่อน:

- [ ] สลับ tab ทั้ง 5 แล้ว panel ที่ถูกต้องแสดง (คนอื่น `display:none`)
- [ ] scroll แล้ว tab bar ไม่ทับ/ไม่มุดใต้ header — วัด `topbar.bottom === tabs.top`
- [ ] ปุ่มกับ select ในแถวเดียวกันสูงเท่ากัน (regression ของ 34px)
- [ ] queue เปิดมากรอง `needs_review` และ badge ตรงกับจำนวนแถว
- [ ] `info` / `warning` / `blocking` ได้คนละสี — เทียบ computed color จริง
- [ ] ลบ record แล้วเอกสารกลับมาเป็น `Needs human review` ไม่ใช่ `Posted automatically`
- [ ] empty state พูดถูกตามฟิลเตอร์ (ไม่พูดว่า "ยังไม่มีเอกสาร" ตอนมี 10 ใบแต่ไม่มีใบรอตรวจ)
- [ ] เอกสารที่ posted แล้วไม่มีปุ่ม Delete
- [ ] console ไม่มี error ในทุก tab

**เสร็จเมื่อ:** บั๊กทั้ง 5 ตัวข้างบน ถ้าใส่กลับเข้าไป ต้องมีเทสแดง

**ประมาณ:** 1–2 วัน · คุ้มที่สุดในลิสต์นี้

## 2. ~~`po_amount_within_tolerance` ตี underrun เป็นความผิด~~ ✅ แก้แล้ว 2026-08-06

**บั๊กเดิม กัดมาแล้ว 3 ครั้ง แก้ด้วยการหลบทุกครั้ง**

### หลักฐาน

| ครั้ง | เอกสาร | อาการ |
|---|---|---|
| 1 | Demo ใบ 03 | วางบิลต่ำกว่า PO 5% → โดน block |
| 2 | Demo ใบ 05 | 35,000 กับ PO 38,000 → โดน block |
| 3 | **Demo ใบ 06 (2026-08-05)** | 48,000 กับ PO 72,000 → โดน block |

ทั้งสามครั้งแก้ด้วยการ**ปรับตัวเลข PO ให้พอดี** ไม่ได้แตะกฎ

### ปัญหาคืออะไร

`rules/financial.py:385` — docstring เขียนว่า *"must not **overrun** the purchase
order"* แต่โค้ดทดสอบ `abs(difference)` จึง**จับ underrun ด้วย และเป็น `blocking`**

- เทสมีแต่เคส overrun — **ไม่มีเทส underrun สักข้อ**
- เอกสารในชุดวัดผลที่ trip กฎนี้ ก็เป็น overrun
- แปลว่าพฤติกรรม underrun **ไม่มีใครเขียนถึง ไม่มีใครเทส**

### ทำไมมันสำคัญกว่าที่คิด

**วางบิลต่ำกว่าที่สั่ง ไม่ใช่ความเสี่ยงเรื่องจ่ายเงิน** — ไม่มีใครได้เงินเกิน
แต่กฎเป็น `blocking` แปลว่า **ทยอยส่งของ / progress billing / ของขาดส่งไม่ครบ
ทุกใบเข้าคิวคนหมด**

ขัดกับหลักที่ระบบนี้ยืนอยู่: *ปล่อยของเสียผ่าน = จ่ายเงินผิด · หยุดของดี =
เสียเวลาคนหนึ่งนาที* — underrun เสียเวลาคนโดยไม่กันความเสี่ยงอะไรเลย

### ตัวเลือก

| | ทำอะไร | ผล |
|---|---|---|
| **A** ⭐ | เกิน = `blocking` · ต่ำกว่า = `warning` | ยังเห็นในรายงาน แต่ไม่หยุดเอกสาร |
| **B** | เกินอย่างเดียว ต่ำกว่าไม่สนใจ | ตรง docstring แต่เสียสัญญาณ "วางบิลผิด PO" |
| **C** | ปล่อยไว้ แก้ docstring ให้ตรงพฤติกรรม | ถ้าธุรกิจตั้งใจให้ partial billing ผ่านคน |

## 4. เทสทั้งชุด segfault เป็นครั้งคราว (exit 139) 🟡

**เจอ 1 ครั้งใน ~9 รอบ · reproduce ไม่ได้ · ไม่ผูกกับ branch ไหน**

### หลักฐาน

2026-08-06 รัน `pytest tests/` แล้วได้ `exit=139` (SIGSEGV) โดย
**ไม่มี FAILED/ERROR สักบรรทัด** — คือตายตอนจบ ไม่ใช่เทสข้อไหนตก

ตามล่าต่อ:

| ทดลอง | ผล |
|---|---|
| รันเต็มซ้ำบน branch | exit=0 |
| รันเจาะจง render/pdf/ocr 5 รอบ | exit=0 ทั้ง 5 |
| รันเต็มบน `main` 2 รอบ | exit=0 ทั้ง 2 |

### น่าจะเป็นอะไร

`CLAUDE.md` บันทึกไว้แล้วว่า **PDFium ไม่ thread-safe** และ `render.py` ถือ
module lock อยู่ — segfault ตระกูลนี้เคยเกิดมาก่อน เดาว่าเป็น flake ระดับ
C library ไม่ใช่โค้ด Python

### ทำไมต้องบันทึกไว้

segfault ที่เกิดนานๆ ครั้งคือของที่**ทุกคนกดรันใหม่แล้วลืม** จนวันหนึ่งมันเกิดใน
CI แล้วไม่มีใครรู้ว่าเคยเห็นมาก่อน

- [ ] ถ้าเจออีก ให้ `pytest -p no:randomly -x` แล้วดูว่าตายที่เทสไหน
- [ ] พิจารณา `--forked` สำหรับเทสที่แตะ PDFium เพื่อกันไม่ให้ลาก process หลักตาย
