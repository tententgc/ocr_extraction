# DocuFlow — ตอบคำถาม 3 ข้อ

> ระบบที่อธิบายในเอกสารนี้คือของจริงที่รันได้ ตัวเลขทุกตัวมาจากการวัด ไม่ใช่การประมาณ
> รายละเอียด workflow ทีละขั้นอยู่ใน [ARCHITECTURE.th.md](ARCHITECTURE.th.md)

# 1. Technical Approach & Architecture

**คำถาม:** จะออกแบบ solution นี้ end-to-end อย่างไร เลือก LLM และเทคนิคอะไร (prompting, RAG,
fine-tuning, agents) และจะรับมือกับเอกสารที่หลากหลายและไม่มีโครงสร้างแน่นอนอย่างไร

## 1.1 โจทย์จริงไม่ใช่ "อ่านให้ออก" แต่คือ "รู้ว่าเมื่อไหร่อ่านผิด"

โจทย์บอกว่า *ค่าที่ผิดหลุดไป downstream แพง* ประโยคนี้เปลี่ยนทุกอย่าง

ถ้าวัดกันที่ field accuracy อย่างเดียว ระบบที่แม่น 95% ฟังดูดี แต่ 5% ที่ผิดจะไหลเข้าระบบบัญชีเงียบๆ
โดยไม่มีใครรู้ ระบบที่แม่น 91% แต่**รู้ตัวว่าไม่มั่นใจตรงไหน**และส่งใบนั้นให้คนดู มีค่ามากกว่ามาก

ผมจึงตั้ง metric หลักเป็น **silent error rate** = สัดส่วนเอกสารที่ auto-post ไปแล้วมีค่า critical ผิด
เป้าหมายคือ 0 และวัดได้จริง

| metric | ค่าที่วัดได้ |
|---|---|
| **Silent error rate** | **0%** |
| จับ defect ที่ปลูกไว้ | 8/8 |
| ความแม่นในการแยกประเภทเอกสาร | 100% |
| Field accuracy | 91.2% |

## 1.2 สถาปัตยกรรม 4 ชั้น

```
ชั้น 1  OCR          Typhoon OCR 1.5 (cloud / Ollama / MLX) + fallback chain
ชั้น 2  Extraction   LLM 2 ตัวอ่านอิสระ + evidence grounding
ชั้น 3  Validation   30 กฎ deterministic + กฎที่ผู้ใช้เขียนเอง
ชั้น 4  Agent        tool-calling สืบสวน (รันเฉพาะเมื่อ check ไม่ผ่าน)
```

**ทำไมแยกชั้นแบบนี้:** แต่ละชั้นจับ error คนละแบบ OCR พลาด → grounding จับ,
model เดาส่ง → channel ที่ 2 ไม่เห็นด้วย, ค่าถูกแต่ผิดกฎธุรกิจ → validation จับ

## 1.3 เลือก LLM อย่างไร

**ไม่ผูกกับตัวใดตัวหนึ่ง** — ทำเป็น plugin registry ทั้ง OCR และ agent สลับได้จาก dropdown บนหน้าเว็บ
ตอนนี้รองรับ Typhoon Cloud, Ollama (local), MLX (Apple Silicon), OpenAI, Anthropic

การเลือก default มาจากการ **benchmark จริง** ไม่ใช่ความเชื่อ:

| OCR engine | ผลที่วัดได้ |
|---|---|
| **Typhoon OCR 1.5** | อ่านสแกนภาษาไทยได้ถูกต้อง — เป็น default |
| Claude Sonnet 5 vision | อ่านถูกเช่นกัน แต่แพงกว่าและช้ากว่าสำหรับงาน OCR ล้วน |
| **gpt-5.1 vision** | ⚠️ **hallucinate** บนสแกนไทย — แต่งชื่อบริษัทและที่อยู่ที่ไม่มีบนหน้า |

ผลที่สำคัญที่สุดจาก benchmark: **silent error rate = 0% กับ engine ทุกตัว** แม้แต่ตัวที่ hallucinate
คุณภาพ engine เลื่อน straight-through rate ขึ้นลง แต่ไม่ได้ตัดสินว่าค่าผิดจะหลุดไปหรือไม่ —
ตัวที่ตัดสินคือ grounding + 2 channel + validation

## 1.4 เทคนิคที่ใช้ และที่ตั้งใจไม่ใช้

### ✅ Two-channel extraction — เทคนิคหลัก

อ่านเอกสารเดียวกัน **2 รอบ ด้วย model คนละตัว และกรอบคำถามคนละแบบ**

| | Channel 1 | Channel 2 |
|---|---|---|
| กรอบคำถาม | field-first — "หา field นี้" | label-first — "หา label ก่อน แล้วอ่านค่าถัดไป" |
| เห็นคำตอบอีกฝั่ง | ไม่เห็น (blind) | ไม่เห็น (blind) |
| model | Typhoon v2.5 30B | gpt-5.1 (เลือก backend ที่ต่างเสมอ) |

**ทำไมต้องคนละ model:** model ตัวเดียวอ่าน 2 รอบจะผิดซ้ำแบบเดิม สัญญาณ "ตรงกัน" จึงไร้ความหมาย
`resolve_verify_llm` บังคับเลือก backend ที่ต่าง และ**ข้าม backend ที่กำลังรัน OCR อยู่**

ผลลัพธ์: ตรงกัน → 0.97, **ขัดกัน → 0.45** (ต่ำกว่าเกณฑ์ auto-post มาก) — ตัวนี้แหละที่ทำให้ silent error = 0

> เดิม channel ที่ 2 เป็น regex ซึ่งพังกับ layout ที่ไม่ได้เขียนรองรับ แล้ว**เงียบๆ ยุบเหลือ channel เดียว**
> ทำให้สัญญาณ agreement ไม่มีความหมาย — เปลี่ยนมาเป็น LLM ตัวที่สองแล้ว

### ✅ Evidence grounding — ทุกค่าต้องมีที่มา

model ต้องยก**ข้อความจริงจากหน้า**มาประกอบทุก field แล้วระบบตรวจ 2 ชั้น:
1. ข้อความนั้นมีบนหน้าจริงไหม (fuzzy ≥ 88%)
2. ข้อความนั้นระบุค่าที่ตอบมาจริงไหม — **เทียบตามชนิดข้อมูล** วันที่เทียบเป็นวันที่ ตัวเลขเทียบเป็นตัวเลข

การเทียบตามชนิดสำคัญมาก: `INVOICE DATE 11/02/2019` **คือ** การระบุวันที่ `2019-02-11`
การเทียบแบบ substring ตรงๆ จะบอกว่านี่คือ hallucination ซึ่งผิด และเกิดกับเอกสารที่เขียนวันที่แบบ
วัน/เดือน/ปี **ทุกใบ**

และถ้า **2 channel ได้ค่าตรงกัน + ต่างก็ยกข้อความที่มีจริงบนหน้า** → ถือว่า grounded
เพราะการอ่านอิสระ 2 ครั้งแล้วตรงกันคือหลักฐานแข็งแรงกว่าการที่ quote เดียวมีค่านั้นอยู่ข้างใน
(แต่ยังบังคับว่า quote ต้องมีอยู่จริง — 2 channel เห็นตรงกันแต่แต่งข้อความขึ้นมา ยังถือว่าไม่ผ่าน)

### ✅ Confidence ที่คำนวณ ไม่ใช่ที่ model บอก

model บอก confidence ตัวเองได้ห่วยมาก (calibration แย่) เราจึงคำนวณจากสิ่งที่ตรวจสอบได้:

```
ฐาน:  2 channel ตรงกัน 0.97 | ขัดกัน 0.45 | channel เดียว+grounded 0.86 | ลอยๆ 0.30
คูณ:  คุณภาพ OCR × degraded 0.90 × critical แต่ไม่ grounded 0.60 × มี note 0.85
```

### ❌ RAG — ไม่ใช้ และมีเหตุผล

RAG แก้ปัญหา "ข้อมูลไม่อยู่ใน context" แต่ที่นี่เอกสารทั้งใบอยู่ใน context อยู่แล้ว
สิ่งที่ต้องเทียบคือ master data ซึ่งเป็น **structured lookup** — vendor, PO, contract
การเอา vector search มาแทน SQL lookup ที่แม่น 100% คือการเปลี่ยนของที่ถูกแน่นอนเป็นของที่ถูกโดยประมาณ

### ❌ Fine-tuning — ไม่ใช้ในเฟสนี้

ต้องใช้ข้อมูล label เยอะ ผูกกับ model รุ่นนั้น และ retrain ทุกครั้งที่ layout เปลี่ยน
ระบบเก็บ **correction ที่คนแก้** ไว้แล้ว (ตาราง `corrections` + หน้า Insights บอก hotspot)
ซึ่งเป็น dataset ที่จะใช้ fine-tune ได้เมื่อพิสูจน์แล้วว่าคุ้ม — แต่ยังไม่ใช่ตอนนี้

### ✅ Prompting ที่สั้นและเฉพาะเจาะจง

prompt หลัก 7 บรรทัด / 466 ตัวอักษร ไม่ใช่เพราะประหยัด token แต่เพราะ **prompt ยาวคือ prompt ที่ทดสอบไม่ได้**
prompt ที่แยกกันชัดเจน: extraction (field-first), verification (label-first), reconciliation, rule authoring

## 1.5 รับมือเอกสารที่หลากหลายอย่างไร

| ความหลากหลาย | วิธีรับมือ |
|---|---|
| **layout ไม่แน่นอน** | ไม่มี template เลย — LLM อ่านความหมาย ไม่ใช่ตำแหน่ง |
| **ประเภทเอกสารต่างกัน** | classify ก่อน แล้วเลือก schema (invoice 14 field / contract 13 / form 11) |
| **ภาษาไทย + อังกฤษ** | Typhoon OCR เทรนภาษาไทย, normalizer รองรับเลขไทย ๐-๙ และ พ.ศ. |
| **สแกนคุณภาพต่ำ** | quality scoring → escalate ไป engine ถัดไป → ถ้ายังแย่ mark degraded และหักความมั่นใจ |
| **เอกสารที่ไม่เคยเห็น** | `unknown` schema + free mode สำหรับสำรวจ |
| **ค่าที่ไม่ได้พิมพ์บนหน้า** | เช่นสกุลเงินที่ไม่มีรหัส → เดาจากบริบท แต่ mark `inferred` และ**ไม่มีวัน auto-post** |

# 2. Agentic Workflow & Automation

**คำถาม:** จะออกแบบ automated workflow อย่างไร (ingestion → extraction → validation → posting)
ตรงไหนควรใช้ agent/tools ตรงไหนควร deterministic และจะจัดการ human-in-the-loop อย่างไร

## 2.1 เส้นแบ่ง: agent ตรงไหน deterministic ตรงไหน

นี่คือคำถามที่สำคัญที่สุดในข้อนี้ คำตอบของผมคือ:

> **ใช้ LLM ตอนที่ต้อง "ตีความ" ใช้โค้ดตอนที่ต้อง "ตัดสิน"**

| ขั้นตอน | ใช้อะไร | เหตุผล |
|---|---|---|
| อ่านหน้า (OCR) | **LLM** | ต้องตีความ layout ที่ไม่แน่นอน |
| แยกประเภท | keyword → **LLM** เมื่อก้ำกึ่ง | keyword พอสำหรับเคสชัด ประหยัดและเร็วกว่า |
| สกัด field | **LLM × 2** | ต้องเข้าใจว่า label ไหนหมายถึงอะไร |
| normalize | **โค้ด** | พ.ศ.→ค.ศ., เลขไทย, comma — deterministic ล้วน |
| grounding | **โค้ด** | เป็นการเทียบข้อความ ไม่ใช่การตัดสินใจ |
| คำนวณ confidence | **โค้ด** | เป็นสูตรที่อธิบายได้ |
| **ตรวจกฎธุรกิจ** | **โค้ด** | ⬅ สำคัญที่สุด |
| ตัดสิน auto-post | **โค้ด** | ต้องอธิบายได้ว่าทำไม |
| สืบสวนเมื่อผิด | **Agent + tools** | ต้องสำรวจข้อมูลหลายทางแบบไม่รู้ล่วงหน้า |

**ทำไม validation ต้องเป็นโค้ด:** model ที่ตัดสินว่า VAT ถูกไหม คือ model ที่ถูกเอกสารโน้มน้าวได้
ถ้าใบแจ้งหนี้เขียนว่า "VAT exempt per agreement" model อาจเชื่อ โค้ดไม่เชื่อ
และเนื้อหาในเอกสารคือสิ่งที่ supplier ควบคุมได้ 100%

## 2.2 Agent ที่มีจริง — tool-calling loop

Agent **ไม่ได้รันทุกใบ** รันเฉพาะเมื่อ check ไม่ผ่านแล้วเท่านั้น (คุมทั้งต้นทุนและ latency)

```
check ไม่ผ่าน → agent เริ่มสืบสวน
   │
   ├─ read_document(page)          อ่าน OCR ดิบ
   ├─ lookup_vendor(name, tax_id)  ค้น master file
   ├─ lookup_purchase_order(ref)   ดึง PO มาเทียบ
   ├─ lookup_contract(ref)         ดึงสัญญามาเทียบ
   ├─ find_posted_records(...)     หา record ที่ post ไปแล้ว
   ├─ check_arithmetic(...)        คำนวณซ้ำแบบ deterministic
   └─ validate_tax_id(id)          ตรวจ checksum เลขผู้เสียภาษีไทย
   │
   └─► สาเหตุที่แท้จริง + การกระทำที่แนะนำ + correction (ที่ต้อง grounded)
```

**บทเรียนจากของจริง:** agent เคย **แต่งคู่ค้าขึ้นมา** — ตอบว่า "คู่ค้าที่แท้จริงคือ Chao Phraya ซึ่งมี
tax ID ตรงกัน" ทั้งที่ไม่มีการสกัด tax ID มาเลย ต้นเหตุคือ tool คืน field ชื่อ `closest` เฉยๆ
แก้โดยเปลี่ยนชื่อเป็น `similar_names_only` พร้อมคำเตือนชัดเจนว่า *ชื่อเหล่านี้ไม่ใช่คู่ค้ารายนี้
และรหัสของพวกเขาไม่ใช่ของเอกสารใบนี้*

→ **การออกแบบ tool schema สำคัญพอๆ กับ prompt** ชื่อ field ที่กำกวมทำให้ agent เดา

## 2.3 Workflow เต็ม

```
ingestion ──► render ──► ocr ──► classify ──► extract ──► line_items
                                                 │
                                          2 LLM channels
                                                 │
                                              validate ──► route
                                                              │
                              ┌───────────────────────────────┼──────────────┐
                              ▼                               ▼              ▼
                         auto_post                     needs_review      rejected

                                                              │

```

## 2.4 Human-in-the-loop ออกแบบอย่างไร

**หลักการ: คนควรได้เห็นเฉพาะใบที่ต้องใช้วิจารณญาณ และเมื่อเห็นแล้วต้องตัดสินใจได้เร็ว**

สิ่งที่คนตรวจเห็นในหน้าเดียว:
1. **ภาพหน้าเอกสารจริง** อยู่ข้างๆ ค่าที่สกัดได้
2. **evidence quote** ของทุก field — ชี้ได้ว่าค่านี้มาจากตรงไหน
3. **confidence รายตัว** + ธง `unverified` / `inferred`
4. **ผลกฎทุกข้อ** พร้อมเหตุผลว่าทำไมไม่ผ่าน
5. **บทวิเคราะห์ของ agent** — สาเหตุและข้อเสนอแก้

**สิ่งสำคัญ:** เมื่อคนแก้ค่าแล้ว ระบบ **ตรวจกฎใหม่ทั้งชุด** ไม่ใช่ปล่อยผ่าน
เพราะการแก้ที่ซ่อมปัญหาหนึ่งอาจสร้างอีกปัญหาหนึ่ง และ approve จะถูกปฏิเสธถ้ายังมี blocking rule ค้างอยู่

**Feedback loop:** ทุก correction ถูกบันทึกใน `corrections` → หน้า Insights แสดง hotspot ว่า
field ไหนคนแก้บ่อยที่สุด = บอกตรงๆ ว่าควรไปพัฒนาความแม่นตรงไหนต่อ

## 2.5 การควบคุมโดยผู้ใช้ (หน้า Settings)

ทีมธุรกิจปรับเองได้โดยไม่ต้องแก้โค้ดและไม่ต้อง restart:

- **เกณฑ์ auto-post** — slider 0–100%
- **ปิดกฎเป็นรายข้อ** — 30 กฎ มี checkbox แยก
- **Free mode** — ปิดกฎทั้งหมด (สำหรับสำรวจเอกสารสุ่มจากอินเทอร์เน็ต)
- **เขียนกฎใหม่ด้วยภาษาคน** — LLM compile เป็น expression ครั้งเดียว แล้วรันด้วยโค้ด

**ทุกการผ่อนเกณฑ์ขึ้นเตือนค้างไว้** — free mode, กฎที่ปิด, threshold ต่ำกว่า 60%
เพราะการปิด check เงียบๆ คือความล้มเหลวที่แย่ที่สุดของระบบแบบนี้

# 3. Getting It Done & Proving Value

**คำถาม:** จะพิสูจน์คุณค่าเร็วๆ อย่างไร วัดความสำเร็จด้วยอะไร และจะขยายผลอย่างไร

## 3.1 พิสูจน์คุณค่าอย่างไร — ของที่รันได้ ไม่ใช่ slide

สิ่งที่ส่งมอบคือ **platform ที่ใช้งานได้จริง** ไม่ใช่ prototype:

```bash
docuflow serve      # เปิดเว็บ ลากไฟล์ใส่ ได้ผลทันที
```

- ลากไฟล์เข้าไป หรือใส่ **URL ของเอกสารสุ่มจากอินเทอร์เน็ต** ก็ได้
- อัปโหลดหลายไฟล์พร้อมกัน → เข้า queue รันตามลำดับ
- เห็นทุกขั้นตอนของ pipeline พร้อมเวลาที่ใช้
- เห็น record ที่เขียนลงระบบปลายทางจริง

**Demo corpus 10 ใบ** ที่ปลูก defect ไว้ 8 แบบ — เลขคณิตผิด, คู่ค้าไม่รู้จัก, PO ไม่มีอยู่จริง,
เอกสารซ้ำ, บัญชีธนาคารไม่ตรง, tax id checksum ผิด, สกุลเงินไม่ตรง PO, สแกนคุณภาพต่ำ

## 3.2 วัดความสำเร็จด้วยอะไร

### metric หลัก — Silent error rate

> สัดส่วนเอกสารที่ระบบ auto-post ไปแล้ว มีค่า critical ผิด

**ตอนนี้ = 0%** และนี่คือตัวเดียวที่ธุรกิจสนใจจริงๆ เพราะมันคือ "เงินที่จ่ายผิด"

### metric รอง

| metric | ค่า | ความหมาย |
|---|---|---|
| จับ defect ที่ปลูกไว้ | 8/8 | ไม่มีของเสียหลุด |
| Doc-type accuracy | 100% | แยกประเภทถูกหมด |
| Field accuracy | 91.2% | ความแม่นดิบ |
| Straight-through rate | — | สัดส่วนที่ไม่ต้องใช้คน = ตัวประหยัดต้นทุน |

**ทำไมไม่ตั้งเป้า straight-through rate ให้สูงที่สุด:** ดัน STP ขึ้นได้ง่ายมากด้วยการลด threshold
แต่นั่นคือการแลก silent error กับความเร็ว ซึ่งเป็นการแลกที่ผิดทางสำหรับงานการเงิน
วิธีที่ถูกคือ **ปรับปรุงความแม่นให้ confidence สูงขึ้นเอง** แล้ว STP จะตามมา

### ROI คำนวณอย่างไร

```
เวลาที่ประหยัด = (เอกสารทั้งหมด × เวลาต่อใบเดิม)
               − (เอกสารที่เข้าคิว × เวลาตรวจต่อใบ)
               − (เอกสารที่ auto-post × 0)
```

หน้า Insights แสดงตัวเลขนี้จากข้อมูลจริงที่วิ่งผ่านระบบ ไม่ใช่การประมาณ

## 3.3 พิสูจน์ให้เร็ว — ทำอะไรไปแล้วบ้าง

**ทุกอย่างในระบบนี้ทดสอบได้และทดสอบแล้ว:**

- **362 automated tests** ครอบ normalize / grounding / merge / rules / pipeline / API / queue / archive
- **eval harness** วัด field accuracy กับ ground truth
- **benchmark** เทียบ OCR engine 6 ตัว ในโหมด strict

**บทเรียน — benchmark ที่หลอกตัวเอง:** ตอนแรก `pdftext` ได้คะแนน 95.7% ซึ่งดูดีเกินจริง
สืบแล้วพบว่ามัน**ตกไปใช้ cloud OCR** ผ่าน fallback chain จึงเพิ่ม `OCR_STRICT` ที่วัดเฉพาะ engine
ที่สั่งจริง คะแนนจริงคือ **61.4%** — benchmark ที่วัดสิ่งที่ไม่ได้ตั้งใจวัด แย่กว่าไม่มี benchmark

## 3.4 บั๊กที่เจอจากการรันจริง (และแก้แล้ว)

ส่วนนี้สำคัญ เพราะแสดงว่าระบบถูกใช้จริงไม่ใช่แค่เขียนเสร็จ:

| ปัญหา | ผลกระทบ | สาเหตุ |
|---|---|---|
| วันที่ถูกต้องขึ้น "unverified" | confidence 84% → 40% **ทุกใบ**ที่เขียนวันที่แบบ วว/ดด/ปป | เทียบ substring แทนเทียบเป็นวันที่ |
| Typhoon OCR local ถูกนับเป็น fallback | หัก 0.90 ทุกเอกสาร, auto-post ไม่ผ่านทั้งที่อ่านถูก | เช็คด้วยรายชื่อ provider ที่ hardcode |
| เอกสารใบเดียวใช้เวลา >10 นาที | ใช้งานไม่ได้เลย | verify channel ไปแย่ง Ollama กับ OCR |
| batch upload ทำ **segfault ทั้ง process** | server ตาย | PDFium ไม่ thread-safe |
| grounding พังเพราะ HTML table | ทุก field ในตารางขึ้น unverified | tag `<td>` กลายเป็นคำว่า "td" |
| agent แต่งคู่ค้าขึ้นมา | ข้อมูลผิดในบทวิเคราะห์ | tool schema ใช้ชื่อ field กำกวม |

## 3.5 ขยายผลอย่างไร

### เทคนิค

- **Plugin registry** — เพิ่ม OCR engine หรือ LLM ใหม่ = `register_ocr(...)` 1 ครั้ง ได้ทั้ง factory + dropdown + benchmark
- **Schema-driven** — เอกสารประเภทใหม่ = เพิ่ม `DocumentSchema` ไม่ต้องแตะ pipeline
- **กฎเป็น decorator** — `@rule("invoice")` 1 บรรทัด
- **กฎที่ผู้ใช้เขียนเอง** — ไม่ต้องรอ developer เลย
- **Batch queue** — worker count ปรับตาม engine (local 1, cloud 4)
- **Archive แยกตามประเภท** — retention/export ต่อประเภททำได้ในระดับ filesystem

### ที่ต้องทำต่อถ้าขึ้น production จริง

1. **Queue ข้ามเครื่อง** — ตอนนี้เป็น in-process thread pool เหมาะกับ 1 server
2. **Auth + audit ระดับผู้ใช้** — `audit_log` มีแล้ว แต่ยังไม่มี identity
3. **เชื่อม ERP จริง** — ตาราง `records` เป็น stand-in ที่ interface ชัดเจนอยู่แล้ว
4. **Fine-tune จาก corrections** — ข้อมูลกำลังสะสมอยู่ รอให้พิสูจน์ว่าคุ้ม

### แผน rollout ที่แนะนำ

```
เฟส 1  shadow mode      ระบบรันคู่กับคน เทียบผลกัน ไม่ post จริง  → วัด silent error
เฟส 2  auto-post บางส่วน  เปิดเฉพาะ vendor ที่รู้จักและยอดต่ำ       → threshold สูงไว้ก่อน
เฟส 3  ขยายขอบเขต        ค่อยๆ ลด threshold ตามที่ข้อมูลรองรับ     → ดู hotspot เป็นตัวนำ
```

**เฟส 1 สำคัญที่สุด** เพราะให้ตัวเลข silent error rate จริงจากเอกสารของธุรกิจนั้นเอง
ก่อนที่จะมีเงินสักบาทเคลื่อนไหวจากการตัดสินใจของระบบ
